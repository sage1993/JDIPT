# JDIPT v0.2 Legal Analysis and Output Design

## 목적

JDIPT의 기본 법률검토 답변을 다음 두 방향으로 동시에 개선한다.

1. 내부 판단은 더 구조화한다: 법적 대상·행위 특정 → 정의·분류 → 적용 규정 → 규정 관계 → 사실관계 대입 → 문제 발생 지점 → 법령해석 → 논리검증 → 결론.
2. 사용자 출력은 더 단순화한다: 질의요지 → 검토결론 → 검토이유 → 관련 법령 및 자료.

현재 기본 1~6 출력 구조는 법적 정의, 사실관계, 관련 법령, 쟁점, 법률검토, 첨부자료를 서로 다른 H1으로 강제한다. 새 기능까지 같은 방식으로 노출하면 논증이 과도하게 분절되므로, 내부 분석 단계와 사용자 출력 구조를 분리한다.

## 범위

### 포함

- 기본 법률검토형의 출력 계약을 4단 구조로 변경한다.
- 법적 쟁점 매핑(Legal Issue Mapping)을 법령해석보다 선행하는 내부 필수 Gate로 추가한다.
- 검토결론을 상세 검토이유보다 먼저 제시하는 Answer-first 계약을 추가한다.
- 단일 쟁점의 검토이유는 정의·규정·사안 적용·해석을 연속 논증으로 작성하는 Narrative Coherence 계약을 추가한다.
- 독립 쟁점이 둘 이상일 때만 검토이유 내부에 소제목을 사용한다.
- 22-0351, 17-0047, 20-0604에서 확인한 법적 분류형·중복규율형·규율공백형 논증 패턴을 내부 참고 패턴으로 추가한다.
- 기존 eval/validator 계약을 새 출력과 새 분석 Gate에 맞게 마이그레이션한다.
- Plugin 버전을 0.2.0으로 올린다.

### 제외

- Korean Law MCP 도구 인터페이스 또는 `korean-law-mcp` 4.12.1 의존성 변경.
- 법제처 제출용 1~3 구조 변경.
- `logic-validation.md`의 형식논리 점수체계·BLOCK 규칙 변경.
- 별도 Agent, JSON 중간 산출물, 외부 데이터 저장소 도입.
- 법적 대상·정의·규정 관계 등의 내부 분석 메모를 사용자에게 그대로 노출하는 기능.

## 아키텍처

최종 처리 흐름은 다음 네 계층으로 고정한다.

1. **Legal Issue Mapping**
   - 질문에서 법적 대상과 적용 구조를 특정한다.
2. **Legal Interpretation**
   - 문언, 정의·참조, 체계, 목적, 연혁, 다른 법령, 판례·해석례를 필요한 범위에서 적용한다.
3. **Logic Validation**
   - 기존 `references/logic-validation.md`의 전제·추론·개념 일관성·반례·BLOCK 검증을 수행한다.
4. **Answer Rendering**
   - 분석 결과를 4단 출력으로 렌더링하며 결론 우선성과 논증 연결성을 보장한다.

## Legal Issue Mapping Gate

### 1. 질문 요소 특정

질문에서 실제 존재하는 정보만 사용해 다음 요소를 특정한다.

- 주체
- 행위
- 대상
- 법적 상태 또는 분류
- 규모·수치·시점 등 적용기준에 영향을 주는 조건
- 사용자가 확인하려는 법적 결과

자료가 없으면 임의로 보충하지 않고 `확인 필요` 상태로 유지한다.

### 2. 법적 정의·분류 확인

다음 순서로 대상의 법적 위치를 확인한다.

- 법정 정의가 있는지
- 하위 유형 또는 상위 개념이 있는지
- 다른 법령의 분류와 연결되는지
- 포함·제외 문구가 있는지
- 질문의 대상이 어느 법적 범주에 위치하는지

정의 확인은 내부적으로 항상 수행하되, 정의가 결론과 무관하면 사용자 출력에서는 최소한으로 축약한다.

### 3. 적용 규범 지도 작성

관련 규정을 단순 목록이 아니라 역할별로 분류한다.

- 정의
- 본칙
- 적용요건
- 예외
- 특례
- 위임
- 적용 제외
- 준용
- 다른 법률의 관련 규정

### 4. 규정 관계 진단

둘 이상의 규정이 문제되면 최소한 다음 관계 중 무엇인지 검토한다.

- 동일 사항의 중복 규율
- 일반규정 / 특별규정
- 누적 적용
- 원칙 / 예외
- 특례 / 특례
- 준용 관계
- 적용 제외
- 규율 공백
- 서로 다른 규율대상

단순히 `특별법 우선`이라고 결론내리지 않고 규율대상·직접 규율 여부·입법목적·조문체계를 확인한다.

### 5. 사실관계와 요건 연결

핵심 요건별로 사실관계를 다음 세 상태로 연결한다.

- 충족
- 불충족
- 확인 필요

확인되지 않은 사실을 결론에 유리하거나 불리하게 임의 생성하지 않는다.

### 6. Issue Breakpoint 특정

`사업계획승인 여부`, `승강기 설치 여부`처럼 결과만 다시 말하지 않는다. 결론을 가르는 실제 법적 연결부를 한 문장으로 특정한다.

예:

- 법적 분류형: 대상이 본칙과 예외 중 어느 범주에 속하는지가 문제이다.
- 중복규율형: 동일 사항을 규율하는 두 기준을 누적 적용하는지 또는 특별규정이 배타적으로 적용되는지가 문제이다.
- 규율공백형: 특별 규율체계가 해당 사항을 실제로 규정하고 있는지, 공백이면 일반법이 보충 적용되는지가 문제이다.

## 해석 패턴

### 법적 분류형 — 22-0351 패턴

대상 정의 → 상·하위 법적 분류 → 본칙 → 예외 해당 여부 → 결론.

핵심은 사용자가 사용한 명칭을 그대로 적용하지 않고 법령상 분류를 먼저 확정하는 것이다.

### 중복규율형 — 17-0047 패턴

규정 A + 규정 B → 동일 사항 규율 여부 → 일반/특별 또는 중복 적용 관계 → 결론.

핵심은 두 규정이 같은 대상과 같은 법적 기능을 규율하는지 확인하는 것이다.

### 규율공백형 — 20-0604 패턴

특별 규율체계 확인 → 문제되는 사항의 직접 규정 존재 여부 → 공백 확인 → 일반법의 보충 적용 여부 → 결론.

핵심은 `두 법령이 모두 관련된다`는 이유만으로 충돌로 취급하지 않는 것이다.

## 기본 출력 계약

별도 출력 형식 지시가 없는 일반 법령해석·법률검토 답변은 다음 네 개의 H1을 순서대로 사용한다.

```markdown
# 1. 질의요지
# 2. 검토결론
# 3. 검토이유
# 4. 관련 법령 및 자료
```

### 1. 질의요지

사용자의 질문과 결론에 필요한 최소 사실을 정리한다. 사용자가 제공하지 않은 사업목적·처분경위·기관입장·당사자 의도를 추가하지 않는다.

### 2. 검토결론

상세 논증보다 먼저 결론을 1~3문장으로 제시한다.

- 결론이 확정 가능한 경우: `적용됩니다`, `적용되지 않습니다`, `○○로 보는 것이 타당합니다`처럼 직접 답한다.
- 필수 사실 또는 전제가 확인되지 않은 경우: 조건부 결론과 `확인 필요`를 명시한다.
- 상세한 근거·연혁·반론은 여기서 장황하게 설명하지 않는다.

### 3. 검토이유

Legal Issue Mapping과 Legal Interpretation 결과를 하나의 연결된 논증으로 작성한다.

기본적으로 다음 요소를 별도 소제목으로 분절하지 않는다.

- 법적 정의
- 적용 규정
- 본칙·예외
- 규정 간 관계
- 사실관계 대입
- 문제 발생 지점
- 해석방법
- 결론

하나의 쟁점이라면 문단의 연결관계로 독자가 `정의 → 규정 → 사안 적용 → 해석 → 결론`을 따라갈 수 있게 한다. 검토이유 마지막에는 `따라서` 등의 방식으로 `# 2. 검토결론`과 동일한 결론을 다시 확인한다.

### 소제목 사용 조건

`# 3. 검토이유` 내부의 `##` 소제목은 서로 독립적으로 판단 가능한 복수의 법적 쟁점이 있을 때만 사용한다.

판단 기준:

> 소제목을 분리한 각각의 항목이 독립적인 법적 질문으로 성립하는가?

성립하지 않으면 같은 논증 안에서 처리한다.

### 4. 관련 법령 및 자료

최종 판단에 실제 사용한 법령·판례·법령해석례·행정규칙·첨부자료를 정리한다. 확인된 공식 URL이 있으면 기존 `source-policy.md`에 따라 자료명 자체에 Markdown 인라인 링크를 사용한다.

## 법제처 제출용 모드

사용자가 `법제처 법령해석요청서`, `법제처 제출용`, `질의요지·갑설·을설` 등을 명시적으로 요청하면 기존 1~3 구조를 그대로 유지한다.

1. 질의요지
2. 해석대상 법령조문 및 관련 법령
3. 대립되는 의견 및 이유

이번 변경은 법제처 제출용 문안의 구조를 변경하지 않는다.

## 논리검증과 비노출

기존 `logic-validation.md` 계약을 그대로 유지한다.

- 전제 누락, 필요조건/충분조건 혼동, 거짓 양자택일, 개념의 미끄러짐 등을 계속 검증한다.
- 갑설·을설의 동일 법률용어 의미가 달라지면 기존대로 BLOCK 처리한다.
- 내부 기호화, 점수표, 오류분류명, 반례 탐색표는 별도 요청이 없는 한 사용자 출력에 노출하지 않는다.
- Legal Issue Mapping의 내부 분류 라벨도 사용자 출력에 기계적으로 노출하지 않는다.

## Eval 계약

기존 E1~E20의 논리·법제처 동작은 보존한다. 기본 출력에 종속된 E19, E21~E26은 새 4단 계약으로 마이그레이션한다.

신규 시나리오는 최소 다음을 검증한다.

- E27: 법적 대상·정의·분류
- E28: 본칙·예외 선택
- E29: 동일 사항 중복규율과 특별규정 판단
- E30: 규율공백과 충돌 구분
- E31: 사용자 사실과 법적 요건 연결
- E32: Issue Breakpoint 특정
- E33: Answer-first
- E34: 단일 쟁점 Narrative Coherence
- E35: 복수 독립 쟁점에서만 소제목 사용
- E36: 22-0351 법적 분류형 Golden Case
- E37: 17-0047 중복규율형 Golden Case
- E38: 20-0604 규율공백형 Golden Case

## 정적 검증 계약

`scripts/validate_repo.py`는 다음을 검사한다.

- `references/legal-issue-mapping.md` 존재 및 핵심 marker.
- `SKILL.md`가 새 Gate를 참조하는지.
- 기본 출력의 정확한 4개 H1 marker.
- 구 기본 1~6 계약이 기본값으로 남아 있지 않은지.
- 법제처 제출용 1~3 구조가 유지되는지.
- E27~E38 marker가 eval에 존재하는지.
- 기존 E10~E20 논리검증 marker가 유지되는지.
- Plugin 자동 적용 계약이 새 4단 출력으로 갱신되었는지.

## 버전 및 배포

이번 변경은 사용자에게 보이는 기본 동작과 출력 contract가 변경되는 기능 릴리스이므로 JDIPT Plugin 버전을 `0.1.0`에서 `0.2.0`으로 올린다.

동기화 대상:

- `package.json`
- `package-lock.json` root package version
- `.codex-plugin/plugin.json`

`korean-law-mcp` 의존성은 `4.12.1`로 유지한다.

## Acceptance Criteria

- 기본 법률검토 답변의 H1은 정확히 4개이며 순서는 `질의요지 → 검토결론 → 검토이유 → 관련 법령 및 자료`이다.
- 상세 검토이유보다 검토결론이 먼저 나온다.
- 단일 쟁점 답변은 내부 분석 단계별 소제목으로 과도하게 분절되지 않는다.
- 복수 독립 쟁점은 필요한 범위에서만 `검토이유` 내부 소제목으로 나뉜다.
- 법적 정의·본칙·예외·규정 관계·사실대입·Issue Breakpoint가 내부적으로 확인된다.
- 중복규율과 규율공백을 구분한다.
- 확인되지 않은 사실을 생성하지 않는다.
- 기존 논리검증 E10~E20이 회귀하지 않는다.
- 법제처 제출용 1~3 구조가 회귀하지 않는다.
- E27~E38이 기대 동작을 충족한다.
- Plugin 자동 적용 smoke test가 새 4단 출력으로 통과한다.
- `python scripts/validate_repo.py`, `npm ci`, `npm audit --omit=dev`, `npm run mcp -- --help`가 성공한다.
