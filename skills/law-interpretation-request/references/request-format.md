# 출력 형식

모든 사용자용 최종 출력은 Markdown으로 작성한다. 사용자가 별도 형식을 명시하지 않으면 **기본 4단 법률검토형**을 사용한다. 법제처 법령해석요청서 등 특정 제출 형식은 사용자가 그 형식을 명시적으로 요청한 경우에만 사용한다.

응답 형식은 먼저 요청 모드를 분류한 뒤 결정한다.

- **일반 법률검토형**: 사용자가 `검토해줘`, `적용되는지 알려줘`, `법령을 해석해줘`처럼 법적 의미·적용관계를 묻는 경우다. **검토 가능한 법적 쟁점이 특정되어 있으면 자료 부족만으로 질문-only 모드로 전환하지 않는다.** 확정 결론에 필요한 사실·날짜·조문 버전이 부족하면 기본 4단 형식 안에서 조건부 결론과 확인 필요사항을 제시한다.
- **명시적 법제처 모드**: 사용자가 법제처 법령해석요청서, 법제처 제출용, 법제처에 물어볼 질의 등을 명시적으로 요청한 경우다. 이때만 법제처 제출 적합성 보정과 1~3 구조를 적용한다.
- **질문-only 모드**: **질문-only 모드는 법적 쟁점·대상·규정 중 무엇을 검토해야 하는지조차 구성할 수 없는 경우에만** 사용한다. 단지 결론을 확정할 자료가 부족한 경우는 이에 해당하지 않는다.
- **추상 fixture 모드**: A/B/P/Q, 가상 규정, 동일 용어 충돌 등 제공된 전제 자체를 검토할 수 있으면 실제 법령명이 없어도 기본 4단 형식으로 답한다.

## 1. 기본 4단 법률검토형 — 기본값

사용자가 별도 형식을 명시하지 않으면 아래 네 개의 최상위 제목을 **문자열과 순서 그대로** 사용한다. 네 항목은 모두 Markdown H1(`#`)이다.

# 1. 질의요지

사용자의 질문이 실제로 무엇을 판단하려는 것인지와 결론에 필요한 최소 사실만 간결하게 정리한다.

규칙:
- 사용자가 직접 질문을 제시했으면 그 법적 판단사항을 우선 반영한다.
- 사용자가 제공하지 않은 사업목적, 처분경위, 기관입장, 당사자의 의도 등을 사실처럼 추가하지 않는다.
- 사실관계가 길더라도 쟁점과 직접 연결되지 않는 내용은 별도 H1으로 분리하지 않는다.
- 결론에 영향을 주는 사실이 누락된 경우 `확인 필요`로 표시한다.
- **1번 항목 이전에는 별도 서론**·요약·검토대상 설명·Skill 호출문자열을 작성하지 않는다.

# 2. 검토결론

법적 판단이 가능한 범위에서 **검토결론을 상세 검토이유보다 먼저** 1~3문장으로 제시한다.

규칙:
- `적용됩니다`, `적용되지 않습니다`, `○○로 보는 것이 타당합니다`처럼 사용자가 바로 판단 결과를 파악할 수 있게 쓴다.
- 사실관계 또는 법적 전제가 확정되지 않았으면 단정하지 않고 `○○인 경우에는 …`, `△△ 여부 확인이 필요합니다`와 같이 조건부로 낮춘다.
- 적용 기준시점·개정법 시행일·경과조치처럼 결론을 좌우하는 자료가 미확인인 경우에도, 그 미확인 상태 자체를 결론에 반영하고 질문-only 응답으로 대체하지 않는다.
- 이 항목에서는 장문의 조문 설명이나 해석론을 먼저 전개하지 않는다.
- `# 3. 검토이유` 말미의 결론과 실질적으로 일치해야 한다.

# 3. 검토이유

`references/legal-issue-mapping.md`와 `references/interpretation-principles.md`에서 확인한 분석 결과를 **하나의 연결된 법률논증**으로 작성한다.

기본적인 논리 흐름은 필요한 범위에서 다음을 포함한다.

1. 직접 적용되는 법적 정의·분류 또는 핵심 규정
2. 본칙·예외·특례·적용 제외·준용 등 규정의 구조
3. 관련 규정 사이의 관계
4. 사용자의 사실관계와 법적 요건의 연결
5. 서로 다른 결론을 가르는 실제 문제 발생 지점
6. 필요한 문언·체계·목적·연혁·판례·법령해석례 검토
7. 반대논거가 실질적으로 존재하는 경우 그 논거와 한계
8. `따라서` 등의 방식으로 검토결론 재확인

### Narrative Coherence 규칙

- 내부 분석 단계가 세분화되어 있다는 이유만으로 이를 그대로 사용자용 소제목으로 변환하지 않는다.
- **단일 쟁점**에서는 `법적 정의`, `적용 규정`, `사안 적용`, `문제 발생 지점`, `해석`, `결론`을 각각 별도 소제목으로 기계적으로 분리하지 않는다.
- 정의 → 규정 → 사실대입 → 해석이 하나의 추론 사슬이면 문단을 자연스럽게 연결하여 독자가 앞뒤 관계를 한 번에 파악할 수 있게 한다.
- `# 3. 검토이유` 내부 소제목은 **서로 독립적으로 판단 가능한 복수의 법적 쟁점**이 있을 때만 사용한다.
- 소제목 사용 판단 기준은 해당 제목을 떼어냈을 때 독립적인 법적 질문으로 성립하는지 여부다.
- 불필요한 표와 체크리스트가 문장 간 논리 연결을 끊는 경우에는 문단형 설명을 우선한다.

복수 쟁점 예시는 다음과 같다.

```markdown
# 3. 검토이유

## 가. 기존 건축물에도 해당 기준이 적용되는지

[연속 논증]

## 나. 수직증축과 수평증축의 적용 범위가 다른지

[연속 논증]
```

반대로 한 쟁점의 내부 분석 단계만 다른 경우에는 위와 같이 나누지 않는다.

# 4. 관련 법령 및 자료

검토에 실제 사용한 법령, 조문, 판례, 법제처 법령해석례, 행정규칙, 자치법규, 공문, 도면, 처분서 등 근거자료를 정리한다.

규칙:
- 해석대상 조문과 직접 관련 조문은 현행 공식 원문과 대조한다.
- 법령명·조문·판례·법령해석례 등 공식자료에는 `references/source-policy.md`에 따라 **현재 실행에서 실제 확인한 완전한 공식 URL**만 Markdown 인라인 하이퍼링크로 사용한다.
- 정확한 URL을 확인하지 못하면 URL을 추측하지 않고 `[공식 링크 확인 필요]`로 표시한다.
- 실제 논증에 사용하지 않은 자료를 형식상 채우기 위해 나열하지 않는다.
- 자료가 없거나 제공되지 않은 경우 `해당 없음`, `제공되지 않음`, `확인 필요` 등으로 표시한다.
- 조건부 결론을 확정하기 위해 필요한 날짜·경과조치·개정 전후 조문·공통 정의기준 등도 `확인 필요 자료`로 정리할 수 있다.

기본 출력 규칙:
- 사용자가 단순히 `검토해줘`, `법령을 해석해줘`, `질의서 작성해줘`라고 한 경우에는 기본 4단 법률검토형을 사용한다.
- 추상적인 A/B/P/Q 법적 논리 시나리오도 검토에 필요한 추상 전제가 충분하면 기본 4단 법률검토형을 사용한다.
- 동일 조문의 동일 용어를 갑설·을설이 다르게 전제하는 경우, **동일 용어 충돌을 식별한 것 자체가 요청된 법적 관계 검토의 결과**이므로 공통 정의가 미확인이라는 이유로 질문-only로 바꾸지 않는다. 실체논거의 우열은 유보하되 충돌 지점과 필요한 자료를 4단 형식으로 설명한다.
- 최상위 제목은 정확히 `# 1. 질의요지` → `# 2. 검토결론` → `# 3. 검토이유` → `# 4. 관련 법령 및 자료` 순서로 쓴다.
- 검토결론을 검토이유보다 먼저 제시하는 Answer-first 원칙을 유지한다.
- 기본 출력에는 별도 `제목`, `요청취지`, `질의 배경 및 사실관계`, `해석상 쟁점`, `법률검토`, `첨부자료` H1을 추가하지 않는다. 필요한 사실·쟁점·자료는 네 항목의 기능에 맞게 통합한다.
- 구 기본 구조인 `# 1. 요청취지` → `# 2. 질의 배경 및 사실관계` → `# 3. 관련 법령 및 조문` → `# 4. 해석상 쟁점` → `# 5. 법률검토` → `# 6. 첨부자료`를 기본 모드에서 사용하지 않는다.
- 업로드된 기준 문서가 있어도 사용자가 그 문서의 형식을 따르라고 명시하지 않았다면 4단 기본 구조를 유지한다. 기준 문서의 문체·논리 전개·표현은 참고할 수 있다.
- 해당 항목에 자료가 없으면 임의로 만들어 채우지 않는다.

## 2. 법제처 법령해석요청서 — 명시적 요청 시에만

사용자가 명시적으로 법제처 법령해석요청서, 법제처 제출용, 또는 `질의요지·갑설·을설` 구조를 요청한 경우에만 다음 1~3 형식으로 전환한다.

법제처 모드의 최상위 H1은 **정확히** 다음 문자열과 순서를 사용한다.

```markdown
# 1. 질의요지
# 2. 해석대상 법령조문 및 관련 법령
# 3. 대립되는 의견 및 이유
```

`# 2. 질의배경`, `# 2. 관계 법령`, `# 3. 의견` 등으로 이름을 줄이거나 바꾸지 않는다.

# 1. 질의요지

가능하면 다음 구조를 사용한다.

> 「A법」 제○조에서는 …라고 규정하고 있고, 같은 법 시행령 제○조에서는 …라고 규정하고 있는바,
>
> [쟁점에 필요한 최소 전제사실]의 경우, [해석 A]로 보아야 하는지, 아니면 [해석 B]로 볼 수 있는지?

하나의 문언 범위를 묻는 경우:

> …라고 규정하고 있는바, 같은 규정의 “○○”는 △△한 경우만을 의미하는지?

규칙:
- 사실관계는 쟁점에 필요한 최소한만 넣는다.
- 이미 존재하는 처분의 위법성 판단처럼 쓰지 않는다.
- 회신기관이 예/아니오 또는 선택지로 답하기 쉽게 만든다.
- 복합 질문은 서로 독립된 법적 쟁점이면 `가.`, `나.`로 분리한다.

# 2. 해석대상 법령조문 및 관련 법령

## 가. 해석대상 법령조문

질의의 결론을 직접 좌우하는 조문을 원문 그대로 정확히 적는다. 법률뿐 아니라 직접 위임된 시행령·시행규칙이 있으면 함께 넣는다.

## 나. 관련 법령

정의규정, 목적규정, 참조규정, 다른 법률 등 해석에 보조적으로 필요한 조문을 넣는다. 없으면 `해당 없음`으로 쓸 수 있다.

법령명·조문번호·항·호·목을 최신 공식 원문과 대조한다.

# 3. 대립되는 의견 및 이유

## 가. 갑설: [결론을 짧게 요약]

- 문언상 …
- 같은 법 제○조 및 시행령 제○조와의 관계를 보면 …
- 입법 목적·연혁·관련 해석례를 고려하면 …
- 따라서 …

## 나. 을설: [반대 결론을 짧게 요약]

동일한 깊이로 반대 논거를 정리한다. 한쪽 근거가 약하면 약한 이유가 드러나도록 쓴다. 억지 논거를 만들지 않는다.

최종 본문 번호는 1~3만 사용하고 `4. 해석요청기관의 의견`부터 `8. 법령해석요청 체크리스트`까지는 생성하지 않는다.

## 3. 정보 부족 응답 — 질문-only는 좁게 적용

**질문-only 모드는 법적 쟁점·대상·규정 중 무엇을 검토해야 하는지조차 구성할 수 없는 경우에만** 사용한다.

예:
- `이 규정 해석 질의서 써줘`처럼 규정 자체가 제공되지 않고 어떤 법적 문제가 쟁점인지도 알 수 없는 경우
- 제출용 질의서를 요청했지만 대상 법령·쟁점·기초 사실이 모두 없어 초안의 대상 자체를 특정할 수 없는 경우

이 경우에는 필요한 질문 3~7개만 제시하고 그 응답에서 중단한다.

반대로 다음은 질문-only 사유가 아니다.

- 법적 쟁점은 특정되어 있으나 확정 결론에 필요한 날짜·경과조치·개정 전후 조문이 미확인인 경우
- 과거 허가와 후속 변경허가처럼 적용 기준시점이 복수라는 구조가 이미 드러난 경우
- 동일 용어 충돌·전제 누락·참조자료 미확인 등 **미해결 지점 자체가 검토결과**인 경우
- 추상 fixture에서 `미확인`, `정보 없음`, `확인 필요` 상태가 전제로 제공된 경우

이 경우에는 기본 4단 형식으로 분석 가능한 구조와 한계를 설명하고 `# 2. 검토결론`을 조건부로 낮춘다. 추가로 필요한 정보는 `# 4. 관련 법령 및 자료` 등에 정리한다.

명시적 법제처 모드에서 구체적 사실판단·처분 위법성 판단을 직접 묻고 제출 형식상 부적합하면서 필수 정보도 부족한 경우에는 부적합 설명 후 필요한 질문만 하고 중단할 수 있다.

## 4. Output Hygiene 및 최종 Rendering Hard Gate

이 절차는 **사용자에게 최종 문자열을 보내기 직전의 마지막 단계**다. 조사·도구 호출·논리검증·초안 작성이 아무리 길어졌더라도 반드시 다시 수행한다. 도구 호출 직전에 수행한 형식 검사는 최종 검사로 인정하지 않는다.

위 3절의 좁은 질문-only 모드로 분류된 응답을 제외하면, 선택한 출력 모드가 아래 검사를 모두 통과하기 전에는 사용자에게 보내지 않는다.

### 4.1 기본 모드 hard-fail 검사

기본 모드 최종 초안에서 다음을 순서대로 검사한다.

1. 앞뒤 공백을 제외한 **첫 비공백 줄이 정확히 `# 1. 질의요지`인지** 확인한다.
2. 줄 시작이 `# `인 최상위 H1만 추출한다.
3. 추출된 H1의 개수가 정확히 4개인지 확인한다.
4. 그 4개가 아래 배열과 문자 단위로 일치하는지 확인한다.

```text
# 1. 질의요지
# 2. 검토결론
# 3. 검토이유
# 4. 관련 법령 및 자료
```

5. 첫 H1 이전에 `결론적으로`, `검토 결과`, `JDIPT를 적용하겠습니다`, `이유는 다음과 같습니다`, 호출 메타데이터, 별도 요약 등 사용자용 서론이 없는지 확인한다.
6. `# 2. 검토결론`이 `# 3. 검토이유`보다 앞에 있고, 결론 또는 조건부 결론이 실제로 그 항목 안에 있는지 확인한다.
7. 계약 외 H1이 없는지 확인한다.

**하나라도 실패하면 그 초안은 폐기하고 4단 구조로 새로 렌더링한다. 실패한 초안을 부분 수정한 채 그대로 보내지 않는다. 재렌더링한 결과에 대해 1~7 검사를 다시 처음부터 수행한다.**

### 4.2 법제처 모드 hard-fail 검사

법제처 모드에서도 같은 방식으로 첫 비공백 줄, H1 개수, 정확한 문자열·순서를 검사한다. 허용되는 H1은 다음 세 개뿐이다.

```text
# 1. 질의요지
# 2. 해석대상 법령조문 및 관련 법령
# 3. 대립되는 의견 및 이유
```

법제처 모드에서는 세 H1의 본문을 모두 작성한 뒤, 문서 말미에 번호 없는 `※ 제출 전 확인` 문단이 실제로 존재하는지도 hard-fail로 검사한다. 이 문단은 H1이 아니므로 3-H1 개수에는 포함하지 않는다. `※ 제출 전 확인`이 없으면 H1이 정확하더라도 초안을 폐기하고 다시 렌더링한다.

하나라도 다르면 초안을 폐기하고 법제처 1~3 구조로 새로 렌더링한 뒤 재검사한다.

### 4.3 Output Hygiene check

- `$law-interpretation-request`, `@jdipt`, `Skill activated`, `Plugin activated` 같은 호출·활성화 메타데이터를 최종 법률검토 문안에 쓰지 않는다.
- Skill/reference 파일명, validator 계약명 등 내부 구현 메타데이터를 사용자가 구현 설명을 요청하지 않는 한 노출하지 않는다.
- 사용자가 직접 제공한 A/B/P/Q 명칭은 필요하면 자연어로 다시 지칭할 수 있다. 다만 모델이 내부 검증을 위해 생성한 논리식·점수·오류분류명은 출력하지 않는다.

### 4.4 URL provenance check

- 모든 URL은 현재 실행에서 실제 확인한 완전한 URL인지 확인한다. 식별자가 비어 있거나 끝이 `=`인 미완성 URL, 기억으로 조합한 URL은 출력하지 않는다.
- 현행법 결론에 사용하는 링크가 현재 실행에서 확인한 현행 버전과 불일치하는 과거 시행본을 가리키지 않는지 확인한다.

## 5. Markdown 규칙

- 모든 사용자용 최종 출력은 Markdown으로 작성한다.
- 기본 모드의 최상위 4개 항목은 반드시 H1(`#`)으로 출력한다.
- 법제처 모드의 최상위 1~3 항목도 H1(`#`)을 기본으로 사용한다.
- 기본 모드에서는 하위 제목을 과도하게 사용하지 않고 Narrative Coherence 규칙을 우선한다.
- 법제처 모드에서는 하위 항목을 `##`, `###`, 목록, 표로 구조화할 수 있다.
- 법령·판례·법령해석례 등 공식자료는 `references/source-policy.md`에 따라 클릭 가능한 Markdown 인라인 하이퍼링크를 우선 사용한다.
- 사용자가 별도 파일 형식을 요청하지 않는 한 HTML 전용 태그나 일반 텍스트 전용 레이아웃을 기본 출력으로 사용하지 않는다.
