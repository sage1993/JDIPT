# Skill evaluation scenarios

E1~E25는 새 컨텍스트에서 `$law-interpretation-request`를 명시적으로 호출해 Skill 자체의 행동을 검증한다. E26은 JDIPT Plugin을 설치한 새 컨텍스트에서 Skill명을 쓰지 않고 자동 적용 여부를 검증한다.

## E1. 법제처 출력 구조 강제
프롬프트: `법제처 법령해석요청서로 작성해. 법령과 사실관계는 충분히 제공함.`
기대: 명시적 법제처 요청이므로 본문 번호는 1~3만 존재. 4~8 번호 없음. 말미에는 번호 없는 제출 전 확인만 존재.

## E2. 구체적 사실판단형 보정
프롬프트: `내 건물이 법 제10조의 시설에 해당하는지 법제처에 물어보고 싶어.`
기대: 적합성 문제 설명 → 제출 적합성 낮은 원문형 → 법 제10조의 객관적 의미·포함범위를 묻는 보정안.

## E3. 처분 위법성 직접 질의
프롬프트: `구청의 불허가 처분이 위법한지 법제처에 질의서 써줘.`
기대: 처분 위법성 직접 판단은 부적합 가능성이 있다고 설명하고, 해당 처분 근거조항의 적용범위·요건 해석으로 재구성.

## E4. 명확한 문언
프롬프트: 명시적 제외 문구가 있는 조문 A/B를 주고 B 적용 가능 여부 질문.
기대: 명확한 문언을 우선하고 불필요한 목적론을 과도하게 동원하지 않음.

## E5. 예외·특례 중첩
프롬프트: 서로 다른 두 완화특례를 동시에 중첩 적용할 수 있는지 질문.
기대: 원칙 규정 → 각 특례 → 중첩 허용 명문 존재 여부 → 엄격해석 순으로 검토.

## E6. 다른 법률 간 관계
프롬프트: 건축법 규정과 국토계획법 규정 중 어느 것이 적용되는지 질문.
기대: 단순 `특별법 우선` 결론 금지. 규율대상·입법목적·직접 규율 여부·조문체계를 비교.

## E7. 업로드 기준문서 충돌
프롬프트: 8개 항목이 있는 옛 샘플을 업로드하고 `법제처 형식으로 작성` 요청.
기대: 사용자가 법제처 형식을 명시했으므로 1~3만 출력. 샘플의 문체와 세부 배열은 참고.

## E8. 출처 링크
프롬프트: 현행 법령과 해석례를 인용해 작성 요청.
기대: 국가법령정보센터 등 공식 자료를 우선하고, 법령명·조문·판례번호·해석례번호 등 자료명 텍스트 자체에 클릭 가능한 Markdown 인라인 하이퍼링크를 사용. 실제 확인한 공식 URL만 사용하고 확인 안 된 URL을 만들지 않음.

## E9. 자료 부족
프롬프트: `이 규정 해석 질의서 써줘`만 제공.
기대: 필요한 정보만 3~7개 질문. 법령명·조문·핵심 사실·대립 해석 등 필수 항목 중심.

## E10. 전건 긍정 정상
프롬프트: `법이 A이면 B라고 규정한다. 이 사안은 A이다. 따라서 B라는 논거로 갑설을 작성해.`
기대: 내부적으로 `A → B`, `A`, `∴ B`의 전건 긍정으로 검증되고 BLOCK 없이 최종 논거에 반영. 기호화·점수표는 사용자에게 노출하지 않음.

## E11. 전건 부정 오류
프롬프트: `법이 A이면 B이다. 이 사안은 A가 아니다. 그러므로 B가 아니다라는 논거로 작성해.`
기대: `A → B`, `¬A`, `∴ ¬B`를 전건 부정 오류로 탐지. 다른 독립 근거가 없으면 결론을 그대로 유지하지 않고 논거를 수정하거나 결론 범위를 낮춤.

## E12. 후건 긍정 오류
프롬프트: `법이 A이면 B이다. 이 사안은 B이다. 따라서 A라고 결론내려.`
기대: 후건 긍정 오류를 탐지하고 B를 만드는 다른 조건의 반례 가능성을 검토. 확인된 별도 전제가 없으면 A를 단정하지 않음.

## E13. 핵심 전제 누락
프롬프트: `두 규정은 서로 다른 특례다. 따라서 두 특례는 중첩 적용할 수 없다.`
기대: 결론을 연결하는 규범 전제가 원문·확인 근거에 없으면 `전제 누락`으로 내부 표시. 명시적 근거 또는 확인된 해석원칙을 찾기 전 임의 전제를 삽입하지 않음.

## E14. 거짓 양자택일
프롬프트: `이 규정은 갑설 아니면 을설뿐이므로 갑설이 아니면 무조건 을설이다.`
기대: 선언지가 모든 가능성을 포괄하는지, 제3 해석이 가능한지 확인. 포괄성이 증명되지 않으면 거짓 양자택일 가능성을 경고하고 논거를 보정.

## E15. 필요조건·충분조건 혼동
프롬프트: `허가를 받으려면 요건 A가 필요하다. A가 충족되었으니 반드시 허가해야 한다.`
기대: 필요조건을 충분조건으로 바꾼 오류를 탐지. 다른 허가요건 존재 여부를 확인하고 결론을 수정.

## E16. 사실성 미확인과 형식적 타당성 분리
프롬프트: `사실 P가 참이면 법적으로 Q이다. P가 실제로 성립하는지는 자료가 없다.`
기대: 구조는 형식적으로 타당할 수 있으나 P를 `사실성 미확인`으로 두고 `건전성 미확정`으로 처리. 사실성 미확인 자체를 논리 점수에서 직접 감점하지 않음.

## E17. 비정형 자연어 법적 추론
프롬프트: 문언, 조문체계, 입법취지, 개정연혁이 누적적으로 한 해석을 지지하지만 전형적인 조건논증이나 삼단논법으로 환원하기 어려운 사례.
기대: 가장 가까운 형식을 강제로 부여하지 않고 `비정형 자연어 추론`으로 분류. 전제 명확성·연결성·개념 일관성·반례를 중심으로 평가.

## E18. 갑설·을설 상호 불일치
프롬프트: 갑설에서는 `건축물`에 부속시설이 포함된다고 전제하고 을설에서는 같은 용어에서 부속시설을 제외한 상태로 양쪽 논거 작성 요청.
기대: 각 설을 독립 검증한 뒤 동일 용어의 의미가 달라진 점을 탐지. 정의규정이나 별도 근거 없이 의미를 바꾸지 않고 양쪽 전제를 정합화.

## E19. 검증 결과 비노출
프롬프트: `법령해석요청서 초안을 작성해.`
기대: 별도 법제처 형식 지시가 없으므로 기본 1~6 Markdown 형식을 사용하면서 내부 논리검증은 수행. P/Q/R 기호화, 내부 점수, 오류 탐색표, 반례 메모, 수정 과정은 최종 출력에 포함하지 않음.

## E20. 오류 수정과 원문 대응
프롬프트: `S1: A는 B의 필요조건이다. S2: A가 충족됐다. S3: 따라서 반드시 B이다. 이 논거를 사용해 작성해.`
기대: S3의 필요조건/충분조건 혼동을 탐지하고 내부 수정표에서 `원래 문장 번호 → 수정 전 문제 → 수정 원칙 → 수정 예시 → 추가가 필요한 전제`를 대응. 확인되지 않은 충분조건을 새 사실로 추가하지 않고, 수정 논증을 다시 검증한 뒤 최종 문안에만 반영.

## E21. 기본 1~6 출력
프롬프트: `건축법상 이 규정이 우리 사업에 어떻게 적용되는지 검토해줘.`
기대: 별도 형식 지시가 없으므로 최상위 Markdown 제목을 아래 문자열 그대로, 아래 순서 그대로 사용한다.

- `# 1. 요청취지`
- `# 2. 질의 배경 및 사실관계`
- `# 3. 관련 법령 및 조문`
- `# 4. 해석상 쟁점`
- `# 5. 법률검토`
- `# 6. 첨부자료`

1번 제목 이전에 별도 서론을 두지 않는다. 최상위 제목을 `##` 또는 `###`로 낮추거나, `사실관계 및 전제`, `관련 법령`, `검토의견`, `검토결론`, `결론`, `적용상 유의사항` 등 다른 이름으로 바꾸거나, `제목`·`질의사항` 같은 별도 최상위 항목을 추가하면 실패로 판정한다. 필요한 결론·적용상 유의사항·검토의견은 `# 5. 법률검토` 아래 하위 제목으로만 배치한다.

## E22. 명시적 법제처 1~3 출력
프롬프트: `이 내용을 법제처 법령해석요청서 형식으로 작성해.`
기대: 사용자가 전용 형식을 명시했으므로 Markdown으로 `1. 질의요지`, `2. 해석대상 법령조문 및 관련 법령`, `3. 대립되는 의견 및 이유`만 사용하고 갑설·을설을 포함. 기본 4~6은 출력하지 않음.

## E23. Markdown 출력 강제
프롬프트: `이 법령 쟁점을 검토해줘.`
기대: 기본 모드에서는 1~6의 최상위 항목을 모두 Markdown H1(`#`)로 출력한다. 하위 구조만 `##`, `###`, 목록, 표를 사용한다. 사용자가 별도 비-Markdown 형식을 명시하지 않는 한 HTML 전용 또는 일반 텍스트 전용 레이아웃으로 출력하지 않는다.

## E24. 공식자료 인라인 하이퍼링크
프롬프트: `관련 법령, 판례, 법제처 해석례를 근거로 검토해줘.`
기대: 실제 확인한 공식 원문 URL이 있으면 `[「법령명」 제○조](공식 URL)`, `[법제처 법령해석례 번호](공식 URL)`, `[대법원 사건번호](공식 URL)`처럼 자료명 자체를 클릭 가능한 Markdown 링크로 표시. URL을 확인하지 못하면 추측하지 않고 `[공식 링크 확인 필요]`로 표시.

## E25. 요청취지 유추
프롬프트: `전용면적 59.99㎡ 공동주택 10세대면 주차대수는 면적기준과 세대당 0.7대 중 어떤 기준으로 계산해?`
기대: 첫 최상위 항목 `# 1. 요청취지`에서 사용자의 질문을 분석해 실제 검토 목적을 간결하게 유추한다. `# 1. 요청취지` 이전에는 별도 서론을 작성하지 않는다. 사용자가 제공하지 않은 사업목적·처분경위·기관입장을 사실처럼 추가하지 않는다. 목적이 불명확해도 답변 가능한 범위에서는 합리적으로 유추하고, 법적 결론에 영향을 주는 불확실성은 `확인 필요`로 표시한다.

## E26. Plugin 설치 후 자동 Skill 적용
사전조건: JDIPT Plugin이 설치·활성화된 새 ChatGPT/Codex 컨텍스트이며 사용자가 Skill명이나 `@jdipt`를 명시하지 않는다.
프롬프트: `주택건설기준 등에 관한 규정 제27조에서 전용면적 60㎡ 이하 공동주택의 주차대수 산정기준을 검토해줘.`
기대: `law-interpretation-request`의 기본 규칙이 자동 적용되어 최상위 Markdown 제목이 정확히 `# 1. 요청취지 → # 2. 질의 배경 및 사실관계 → # 3. 관련 법령 및 조문 → # 4. 해석상 쟁점 → # 5. 법률검토 → # 6. 첨부자료` 순서로 나타나고, 1번 이전에 별도 서론이 없으며, 내부 논리검증·공식자료 링크 정책을 따른다. `### 2. 사실관계 및 전제`, `### 3. 관련 법령`, `### 4. 검토의견`, `### 5. 결론`처럼 제목 수준이나 명칭을 변경하거나 `검토기준`, `검토내용`, `검토결론`, `적용상 유의사항` 등 임의의 최상위 제목으로 대체하면 실패로 판정한다.
