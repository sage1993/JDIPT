## 기본 출력 통과 조건

- 별도 출력 형식 지시가 없는 일반 법령해석·검토 요청은 다음 최상위 Markdown 제목을 **문자열과 순서까지 그대로** 사용한다: `# 1. 질의요지`, `# 2. 검토결론`, `# 3. 검토이유`, `# 4. 관련 법령 및 자료`.
- 기본 4단 항목은 모두 Markdown H1(`#`)이다. `##` 또는 `###`로 낮추지 않는다.
- `# 1. 질의요지` 이전에는 별도 서론·요약·검토대상 설명·Skill 호출 문자열을 작성하지 않는다.
- `# 1. 질의요지`는 사용자의 질문과 결론에 필요한 최소 사실을 정리한다. 사용자가 제공하지 않은 사업목적·처분경위·기관입장 등을 사실처럼 추가하지 않는다.
- `# 2. 검토결론`은 상세 검토이유보다 먼저 나타나며, 법적 판단이 가능한 범위에서 결론을 1~3문장으로 명확하게 제시한다.
- 검토결론은 상세 검토이유보다 먼저 제시한다.
- 결론에 필요한 전제가 확인되지 않았으면 `확인 필요` 또는 조건부 결론으로 낮추고 임의로 사실을 보충하지 않는다.
- `# 3. 검토이유`에서는 정의·분류, 적용 규정, 규정 관계, 사실대입, 문제 발생 지점, 해석을 하나의 연결된 법률논증으로 작성한다.
- 단일 쟁점을 `법적 정의`, `적용 규정`, `사안 적용`, `문제 발생 지점`, `해석`, `결론` 같은 내부 분석 단계별 소제목으로 기계적으로 분리하지 않는다.
- `# 3. 검토이유`의 하위 소제목은 **서로 독립적으로 판단 가능한 복수의 법적 쟁점**이 있을 때만 사용한다.
- `# 3. 검토이유` 말미의 최종 판단은 `# 2. 검토결론`과 실질적으로 일치한다.
- `# 4. 관련 법령 및 자료`에는 실제 논증에 사용한 법령·조문·판례·해석례·행정규칙·첨부자료를 정리한다.
- 기본 출력에 `# 1. 요청취지`, `# 2. 질의 배경 및 사실관계`, `# 3. 관련 법령 및 조문`, `# 4. 해석상 쟁점`, `# 5. 법률검토`, `# 6. 첨부자료`의 구 기본 구조를 추가하지 않는다.
- 법제처 1~3 구조는 사용자가 `법제처 법령해석요청서`, `법제처 제출용`, `질의요지·갑설·을설` 등 전용 형식을 명시적으로 요청한 경우에만 사용한다.
- 법제처 모드의 최상위 H1은 정확히 `# 1. 질의요지`, `# 2. 해석대상 법령조문 및 관련 법령`, `# 3. 대립되는 의견 및 이유`다. `질의배경`, `관계 법령`, `의견` 등으로 제목을 바꾸지 않는다.
- 법제처 모드 본문이 정확히 1~3 구조를 따르며 `4. 해석요청기관의 의견`, `5. 민원인 의뢰 여부`, `6. 법령소관 중앙행정기관 장의 의견`, `7. 참고자료`, `8. 법령해석요청 체크리스트`를 생성하지 않는다.
- 모든 사용자용 최종 출력은 Markdown으로 작성한다.
- 부적합 질의는 이유 설명이 초안보다 먼저 온다.
- 원문형 초안에는 제출 적합성이 낮다고 표시한다.
- 보정 초안은 객관적 법규범 의미·범위 질문으로 바뀐다.
- 문언이 명확한 경우 해석을 불필요하게 확장하지 않는다.
- 예외·특례·침익 규정에는 엄격해석 원칙을 적절히 적용한다.
- 사실과 법적 평가를 분리하고 불확실성 라벨을 사용한다.

## 자료 부족 조건

- 법령명·조문·핵심 사실 등 실체결론이나 초안 작성에 필수적인 정보가 부족하면 필요한 질문 3~7개만 제시하고 **그 응답에서는 초안 작성을 중단**한다.
- 정보 부족 상태에서 기본 4단 초안, 법제처 원문형 초안 또는 권고 보정 초안을 함께 만들면 실패다.
- 사실과 조문은 충분하지만 질의 형식만 사실판단형·처분 위법성 판단형인 경우에는 설명과 보정 초안을 병행할 수 있다.

## 법적 쟁점 매핑 필수 조건

- 최종 법령해석 전에 `references/legal-issue-mapping.md` 절차를 수행한다.
- 질문에서 주체, 행위, 대상, 법적 상태 또는 분류, 규모·수치·시점, 확인하려는 법적 결과 중 실제 관련 요소를 특정한다.
- 사용자가 가상 규정·정의·본칙·예외·사실관계를 문장으로 직접 제공했으면 이를 검토 전제로 보존한다. 이미 제공된 내용을 다시 `문언 없음`, `정의 없음`, `자료 없음`으로 취급하지 않는다.
- 단순히 `필요한 규정은 모두 제공되었다고 전제해`라고만 하고 실제 규정 내용이 없는 경우에는 구체 규정이 제공된 것으로 간주하지 않는다.
- 법정 정의가 있는 경우 직접 정의 → 상·하위 개념 → 포함·제외 → 다른 법령의 참조·분류 연결 순으로 필요한 범위에서 법적 분류를 확인한다.
- 관련 규정을 단순 나열하지 않고 정의, 본칙, 적용요건, 예외, 특례, 위임, 적용 제외, 준용, 다른 법률 규정으로 역할을 구분한다.
- 둘 이상의 규정이 관련되면 `동일 사항의 중복 규율`, `일반/특별`, `누적 적용`, `원칙/예외`, `특례/특례`, `준용`, `적용 제외`, `규율 공백`, `서로 다른 규율대상`을 구분한다.
- 법 이름만 보고 특별법 우선 또는 누적 적용을 자동 결론내리지 않는다.
- 사실관계와 법적 요건을 `충족`, `불충족`, `확인 필요`로 연결하고 확인되지 않은 사실을 임의로 보충하지 않는다.
- `적용 여부가 쟁점이다`처럼 질문을 반복하는 수준에서 멈추지 않고, 서로 다른 결론을 가르는 실제 **문제 발생 지점**을 특정한다.
- 법적 쟁점 매핑의 내부 라벨, 요건별 상태표, 규정관계 분류표는 사용자가 분석표 공개를 명시적으로 요청하지 않는 한 기본 사용자 출력에 그대로 노출하지 않는다.

## Answer-first 및 Narrative Coherence 조건

- 내부 분석과 논리검증은 결론 확정 전에 수행한다. `결론 우선`은 결론을 미리 정한다는 뜻이 아니라 확정된 결론을 **사용자 출력에서 먼저 배치**한다는 뜻이다.
- `# 2. 검토결론`보다 앞에서 장문의 법령 설명을 시작하지 않는다.
- 단일 쟁점에서는 정의 → 규정 → 규정관계 → 사실대입 → 해석 → 결론이 하나의 추론 사슬이면 문단으로 연결한다.
- 소제목 수 자체를 최소화하는 것이 목적이 아니라, 독립적인 법적 질문이 아닌 내부 분석 단계가 사용자용 목차로 변환되는 것을 방지하는 것이 목적이다.
- 복수의 독립 법적 쟁점이 있으면 `# 3. 검토이유` 내부에서 쟁점별 소제목을 사용할 수 있다. 각 쟁점 내부에서는 다시 단계별 소제목으로 과분할하지 않는다.

## Output Hygiene 조건

- `$law-interpretation-request`, `@jdipt`, `Skill activated`, `Plugin activated` 같은 Skill/Plugin 호출·활성화 메타데이터를 최종 법률검토 문안에 노출하지 않는다.
- Skill/reference 파일 경로, 내부 contract 이름, validator 메타데이터를 사용자가 구현 설명을 요구하지 않는 한 출력하지 않는다.
- 사용자가 직접 A/B/P/Q를 사용한 경우 그 명칭을 자연어 설명에서 다시 지칭하는 것은 허용한다.
- 모델이 내부 검증을 위해 생성한 `A → B`, `P → Q`, `P ∨ Q`, `¬P`, `∴ Q` 등의 형식화, 내부 오류분류명, 점수, 반례표, 수정표는 사용자가 논리감사·형식논리 공개를 요구하지 않는 한 노출하지 않는다.
- 따라서 E16에서 사용자가 직접 제공한 `P`, `Q`를 일반 문장으로 다시 언급했다는 사실만으로 FAIL 처리하지 않는다. 형식논리 메모를 새로 노출했는지를 평가한다.

## URL provenance 및 공식자료 조건

- 공식 법령·판례·법령해석례 등은 **현재 실행에서 실제 확인한 완전한 공식 URL**이 있을 때만 자료명 텍스트 자체에 Markdown 인라인 하이퍼링크를 적용한다.
- 공식 URL을 확인하지 못하면 링크 패턴을 추측하지 않고 `[공식 링크 확인 필요]`로 표시하거나 링크 없이 확인 필요로 둔다.
- `https://www.law.go.kr/LSW/lsInfoP.do?lsiSeq=`처럼 식별자가 비어 있는 URL, 끝이 `=`인 미완성 URL, placeholder가 남은 URL은 실패다.
- 공식 도메인이라는 사실만으로 상세 URL의 provenance가 확인된 것으로 보지 않는다.

## Plugin 적용 조건

- JDIPT Plugin이 **v0.2.0으로 설치·활성화된** 새 컨텍스트에서는 사용자가 Skill명이나 `@jdipt`를 명시하지 않은 일반적인 대한민국 법령해석·법률검토 질문에도 `law-interpretation-request` 규칙이 적용되어야 한다.
- Plugin 자동 적용 테스트는 Skill 직접 호출 테스트와 분리한다. 직접 호출 없이 정확한 H1 4단 구조, Answer-first, Narrative Coherence, Output Hygiene, 내부 논리검증, URL provenance 정책이 나타나는지 확인한다.
- Plugin 설치 상태에서 기본 출력의 최상위 제목 문자열·순서·H1 수준이 다르거나, `# 2. 검토결론`이 상세 이유보다 뒤에 나오거나, 단일 쟁점을 내부 단계별 소제목으로 과분할하면 실패로 판정한다.
- v0.2.0 설치 여부를 확인하지 못한 실행은 **Plugin 행동 PASS로 인정하지 않는다.** 동시에 v0.2.0 자체의 FAIL로도 계산하지 않고 `NOT_EXECUTED` 또는 환경 오류로 기록한다.

## 내부 논리검증 필수 조건

- 최종 문안 생성 전에 `references/logic-validation.md` 절차를 수행한다.
- 각 핵심 논증을 문장 단위로 분해하고 가능한 범위에서 기호화·표준형으로 변환한다.
- 삼단논법, 전건 긍정, 후건 부정, 이중부정, 선언 명제를 우선 판별하되 정확히 일치하지 않으면 `비정형 자연어 추론`으로 분류한다.
- 전건 부정과 후건 긍정을 오류 가능성으로 탐지한다.
- 필요조건/충분조건 혼동, 인과/상관 혼동, 순환논증, 성급한 일반화, 개념의 미끄러짐, 모순, 거짓 양자택일, 근거 부족, 전제 누락, 반례 가능성을 점검한다.
- 원문·확인된 법적 근거에 없는 숨은 전제를 임의로 보충하지 않는다. 필수 연결 전제가 없으면 `전제 누락`으로 처리한다.
- **추상 논리 시나리오의 A/B/P/Q를 사용자가 제시하지 않은 특정 법령·조문·판례·법제처 해석례·개정연혁·사실관계에 임의 대응시키지 않는다.** 사용자가 실체조사를 요청하지 않았다면 추상 상태를 유지한다.
- 선언 명제에서 `갑설 또는 을설`이 가능한 경우 전부라는 **선택지 완전성 자체를 독립 전제**로 검증한다. 완전성이 확인되지 않으면 제3의 가능성을 배제하지 않는다.
- 법제처 모드 또는 갑설·을설 비교에서 **동일한 법률용어의 의미가 양 설 사이에서 달라지면 BLOCK**으로 처리한다. 공통 정의·개념 기준을 먼저 확정하고, 확정할 수 없으면 같은 기준에서 조건부 비교한다.
- 외부 확인이 필요한 전제는 `사실성 미확인`으로 두며, 사실성 미확인 자체를 논리 점수에서 직접 감점하지 않는다.
- 형식적 타당성과 건전성 상태를 분리한다.
- 점수는 형식적 타당성 50, 전제 명확성 20, 근거-결론 연결성 20, 개념 일관성·반례 대응력 10의 합계 100점으로 내부 산정하고 네 항목 점수를 각각 기록한다.
- 판정 구간은 `타당 85~100`, `부분 타당 65~84`, `취약 40~64`, `부당 0~39`를 정확히 사용한다.
- 확신 수준은 `높음`, `중간`, `낮음`으로만 표현한다.
- 법제처 모드에서는 갑설과 을설을 각각 독립 검증한 뒤 사실 전제, 정의, 조문 누락, 숨은 전제, 해석원칙 적용의 일관성을 상호 비교한다.
- 오류 수정 시 가능한 경우 `원래 문장 번호`, `수정 전 문제`, `수정 원칙`, `수정 예시`, `추가가 필요한 전제`를 대응시킨다.
- 누락 전제를 보완하는 예시는 `추가가 필요한 전제`로 원문과 분리하고, 확인되기 전에는 확정 전제로 취급하지 않는다.
- 사실성 미확인 전제를 확정적 사실처럼 고쳐 쓰지 않는다.
- BLOCK 오류가 확인되면 최종 출력 전에 수정하고 다시 검증한다. 확인할 수 없는 누락 전제는 만들어 넣지 않고 조건부 결론 또는 `확인 필요`로 처리한다.

## 내부 검증 비노출 조건

- 사용자가 **논리감사, 형식논리 설명, 검증표 공개**를 명시적으로 요청하지 않은 한 내부 검증 흔적은 최종 답변에 노출하지 않는다.
- 모델이 내부적으로 생성한 기호화·논리식은 내부 전용이다.
- `전건 부정`, `후건 긍정`, `거짓 양자택일` 등의 오류분류명, 항목별 점수표, 반례 탐색표, 내부 수정표는 내부 전용이다.
- 최종 사용자 문안에는 내부 오류분류 대신 그 오류를 교정한 **일반 법률검토 문장**만 반영한다.
- E19는 **정보부족 질문 테스트가 아니라 비노출 테스트**이므로, 필요한 전제와 사실관계를 프롬프트에 충분히 제공한 상태에서 실행한다.

## Golden Case 조건

- E36은 22-0351의 `법적 분류형` 패턴을 검증한다: 대상 정의·분류 → 공동주택 본칙 → 단지형 예외 해당 여부 → 결론.
- E37은 17-0047의 `중복규율형` 패턴을 검증한다: 두 규정의 규율대상·법적 기능 → 동일 사항 여부 → 특별규정의 배타 적용 여부.
- E38은 20-0604의 `규율공백형` 패턴을 검증한다: 특별법이 해당 구체 사항을 직접 규율하는지 → 규율 공백 → 일반법 보충 적용.
- E37과 E38을 같은 `특별법 우선` 규칙으로 기계적으로 처리하면 실패로 판정한다.
- E36~E38 모두 `# 2. 검토결론`과 `# 3. 검토이유` 말미의 결론이 일치해야 한다.
